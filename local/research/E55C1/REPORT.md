## VBlankStart observation point

| Exact order | Pinned source evidence | Consequence |
| --- | --- | --- |
| The due-deadline loop schedules VBlankEnd and the next VBlankStart before calling `processEvent(VBlankStart)`. In cycle-only mode it takes the whole cycle-due batch, then sorts by cycle/type/ID/sequence. | `ps2xRuntime/src/lib/Kernel/EeScheduler.cpp:2557-2576,2622-2655` | The proposed hash is within one start event, not after every event at that cycle. |
| Increment `m_vsyncTick`; call E3/gfx/VU1/E41 note functions; publish `gs().vsyncTick`; call E4/VQ/GS capture; issue GS CSR start operation. | `EeScheduler.cpp:2686-2697` | Tick already advanced. GS work may still be queued. |
| Write guest flag with `writeGuestU32`; conditionally copy 64-bit tick into guest RDRAM; clear guest flag/tick addresses. | `EeScheduler.cpp:2698-2717,2823-2865` | Both guest-visible writes precede hashing. |
| Wake VSync waiters; queue a valid GS callback; dispatch VBlank IRQ cause 2, which queues matching handlers. Both callback and IRQ use `queueInvocation`, not inline guest execution. | `EeScheduler.cpp:2107-2130,2718-2740,1986-2040,1801-1808` | **Candidate point: immediately after line 2739 and before `break` at 2740.** Record `(m_vsyncTick, m_eeCycle, hashes, count)` after VBlankStart bookkeeping and before another event/queued guest invocation runs. |

`m_eeCycle` and `m_vsyncTick` are scheduler members reset in `reset`; `processPendingEvents` asserts the executor and calls the due-event path (`EeScheduler.cpp:357-403,2524-2528`; `ps2xRuntime/include/runtime/ee_scheduler.h:401-436`). Production `PS2Runtime::run` runs `EeScheduler::reset/run` on `GameThread`; the other explicit worker is the GS command thread (`ps2_runtime.cpp:3702-3723`; `gs/gs_worker.cpp:16-23,97-110`). RDRAM, scratchpad and VU1 code/data writes found in `PS2Memory` and the VU1 callbacks execute synchronously on the guest path (`ps2_memory.cpp:1070-1099,1190-1218,1915-1953,2023-2289`; `ps2_runtime.cpp:1030-1065,2630-2639`). **Source inference:** no identified concurrent writer changes these four arrays at the proposed point. This is not a whole-program race proof. The GS worker can still change GS registers/VRAM or process a queued CSR operation, so those are excluded (`ps2_memory.h:323-328`; `ps2_runtime.cpp:973-1003`; `ps2_memory.cpp:1045-1067`). A host thread can enqueue `ExternalWake` under `m_eventMutex`; the executor processes it later, while a 32 MiB scan can delay its wall-time relationship to the guest (`EeScheduler.cpp:842-855,2524-2545,2741-2743`).

## Direct byte regions

| Region/count | API, size, owner/lifetime and direct-read status | Gap |
| --- | --- | --- |

| VU1 program count | **Not found** as an always-on per-runtime execution count/accessor. `VU1Interpreter::execute` starts a program; `resume` continues one (`vu/ps2_vu1_core.cpp:1610-1669`). E36 census covers only enabled, budget-exhausted programs in its window (`ps2_vu1_trace.h:303-323`; `vu/ps2_vu1_core.cpp:1941-1958`). Runtime has VIF1 MSCAL/MSCNT and EE CMSAR1 call sites (`ps2_runtime.cpp:1030-1065,2628-2645`). | Part 2 needs a defined per-runtime count of VU1 `execute` starts (MSCAL and CMSAR1), reset with VU1/runtime state. Exclude `resume`/MSCNT; do not substitute a text label or code-generation count. |

Proposed stable version-1 stream: RDRAM offsets `0..33,554,431`, scratchpad `0..16,383`, VU1 data `0..16,383`, VU1 code `0..16,383`, then the program-start count as **8 explicit little-endian bytes**. Total **33,603,592 bytes** (33,603,584 region bytes + 8 count bytes), streamed without a 32 MiB copy. Report XXH64 for each region and for the complete stream to localize a mismatch. Tick and EE cycle are output metadata, not stream bytes. This is a proposed format, not existing code. The review asks for XXH64 (`docs/research/review-2026-09-23-frontier-2.md:184-186`). Searches of pinned runtime, tests, CMake and tracked filenames found **no XXH64/xxHash implementation or dependency**. Existing FNV routines are a different algorithm (`ps2_e7.h:54`; `ps2_vq.h:44-50`). **Orchestrator choice:** add a small in-tree XXH64 implementation or vendor a pinned upstream xxHash source under fork policy; do not silently substitute FNV. Whichever path is chosen needs a known vector and streaming equivalence test.

## Gaps

- E55A2 fixed RTC and ran one functional boot; E55B2 changed cycle-only event selection and ran one functional boot. Neither is a repeatability proof (`local/research/E55A2/REPORT.md`; `local/research/E55B2/REPORT.md`).
- The pinned fork lacks an always-on VU1 program execution count and XXH64 dependency. The orchestrator must choose count semantics and XXH64 source before Part 2.
- Direct reads appear safe against concurrent writers in the cited production path, but this audit did not run a race test or prove every callback/backend path. `ExternalWake`, live pad input and card contents can still cause divergence.

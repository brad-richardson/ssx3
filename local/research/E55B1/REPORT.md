## Event kinds and distinguishing sequence

`EeEventType` declares, in enum order: **Stop, VBlankStart, VBlankEnd, Dmac, ExternalWake, Alarm** (`ee_scheduler.h:226-241`). That is the type precedence only within one extracted scheduled batch (`EeScheduler.cpp:2579-2593`). In this source, `scheduleEvent` is called for VBlankStart, VBlankEnd, and Alarm (`EeScheduler.cpp:417-419,1748-1750,2602-2609`). Stop uses `requestStop`, and other posted events enter FIFO `m_events` (`EeScheduler.cpp:836-850`); `processPendingEvents` drains that queue after deadlines and timer IRQs (`EeScheduler.cpp:2497-2518`). `processEvent` implements ExternalWake as guest wait completion and Dmac as a no-op (`EeScheduler.cpp:2698-2705`). A targeted fork-wide `rg` found no other `postEeEvent` caller; `PS2Runtime::postEeEvent` simply forwards (`ps2_runtime.cpp:3522-3525`). This does not prove there are no callers outside the searched fork.

Here `C` is guest cycle at entry to `processDueDeadlines` or `waitForEvent`; `T` is arbitrary host time. “Cycle-only” selects by guest deadline, stable same-cycle `(type, ID, insertion sequence)`, with same-cycle memory timer IRQ after scheduled events (the current `processPendingEvents` order). Host pacing may delay an **already chosen** event, but cannot select a different event/cycle. These are source-derived predictions, not executed tests.

## Part 2 recommendation and tests

Recommend one scheduler option, `EeScheduler::setDeterministicEventMode(bool)`, set before `reset`; runtime sets it from exact `PS2X_DETERMINISTIC=1`, while unset or `0` preserves current behavior. The option changes only scheduled deadline and idle timer choice: select by minimum guest cycle and stable same-cycle `(type, ID, insertion sequence)`; choose memory timer by guest cycle, with scheduled events preceding timer IRQs at equality; never use `hostDeadline` to partition, reorder, or pick a fast-forward target. Keep host deadlines only as optional pacing for an already chosen event. The test fixture can inject explicit cycle/host deadlines into the existing private scheduling path without adding a second production switch. The precise pacing policy is a Part 2 design choice, constrained not to feed event/cycle selection.

Focused tests for the Part 2 brief: (1) synthetic same-cycle alarms with reversed host deadlines, asserting ID order in deterministic mode and split-batch legacy order when only the second deadline is host-due; (2) different cycles with reversed host deadlines, asserting cycle order even when both guest deadlines have passed; (3) idle timer cycle 80 versus scheduled cycle 100 with reversed host deadlines, asserting timer IRQ at 80 and A at 100 in deterministic mode versus the existing host choice by default; (4) equal-cycle timer/scheduled event, asserting scheduled-then-timer order; (5) early/late condition-variable wake with no external event, asserting same target, plus separate documentation of posted ExternalWake policy. Use bounded fake/injected host times instead of sleeps for ordering assertions. Existing scheduler/alarm test patterns are at `ps2xTest/src/ps2_runtime_kernel_tests.cpp:937-972,1307-1328`; no test was run here.

**Uncertain event semantics:** ExternalWake is host-arriving and has no guest-cycle timestamp (`EeScheduler.cpp:836-850`); this audit cannot assign its deterministic guest cycle. Dmac is declared but its `processEvent` branch is empty (`ee_scheduler.h:226-234`; `EeScheduler.cpp:2704-2705`); do not infer a DMA ordering rule. RTC, pad neutrality, memory-card isolation, and hash tap are separate E55 work (`docs/research/review-2026-09-23-frontier-2.md:165-190`; `local/research/E55A1/REPORT.md`).

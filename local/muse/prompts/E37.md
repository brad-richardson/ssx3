## Why

E36: all 498 stuck programs/vsync on Select Character run the same vertex
loop (0x418–0x548, exit `IBNE vi03,vi13`) with wild bounds set by the
straight-line setup code between each startPC and 0x418. **PCSX2 runs the
same programs** (T48 records startPCs in 8-byte units: its 0x0/0x2/0x8/0x73
= our 0x0/0x10/0x40/0x398) and they finish in ≤2,090 cycles. T49 captures
the same trace in PCSX2 in parallel; the first differing value names the bug:
same VU memory inputs but different VI results ⇒ an instruction-semantics
bug; different VU memory at MSCAL ⇒ a VIF1 UNPACK/placement bug upstream.

## Change (default off, unit-tested, one commit)

`PS2X_VU1_ENTRY_TRACE=<file>` with `_PCS=0x40,0x10` (byte PCs) and
`_VSYNC=<n>`: for the **first** MSCAL at each listed startPC at or after
vsync n, write:
1. `vumem` : the full 16 KB VU1 data memory at MSCAL entry, one line per
   qword: `vumem <row-dec> <w0> <w1> <w2> <w3>` (hex, 8 digits, x..w).
2. `vif` : every VIF1 command since the previous MSCAL (the packet that fed
   this program): `vif <cmd-name> num=<> addr=<row> fmt=<> usn=<> mask=<hex>
   cl=<> wl=<> [row=/col=] data=<hex words…>` (cap 4096 lines).
3. `pair` : every executed pair from startPC until the first arrival at
   0x418, then 3 loop iterations: `pair pc=0x<byte-pc> up=<hex> lo=<hex>
   <disasm> | vi <i>:<old>-><new> … | vf <n>.<xyzw>:<hex>->… |
   rd <row>:<w0..w3> | wr <row>:<w0..w3>`.
   VI in 16-bit hex; only changed registers; loads/stores give the row.

## Why

E33: on Select Character, 498 of 583 VU1 programs per vsync spend the full
65,536-cycle slice without an E-bit, nothing resumes them, and the 3D rider
is missing. Running them to 16× the budget issued **zero** extra XGKICKs:
the programs are stuck in a loop, not long.

Hypotheses and the observable that separates them (per stuck program):
- **A. Bad input → runaway counted loop.** The loop count comes from the
  program's input header (GIF tag NLOOP / a VI loaded from VU memory), and
  the header is wrong because VIF1 double-buffering (BASE/OFST/TOPS/ITOPS/
  DBF, `TOP`/`ITOP` passed to MSCAL) points at the wrong buffer or the
  UNPACK landed elsewhere. Signature: the loop-exit VI starts at 0 or a
  garbage value; the header qwords at the program's input address are zero
  or stale.
- **B. Wait on unmodeled state.** The loop tests a flag/status the
  interpreter never sets (e.g. an XGKICK-busy or FBRST/VPU_STAT bit via
  `FCAND`/`FSAND`/`FMAND`/`XTOP`/`XITOP`). Signature: the exit condition
  reads a flag or status op, the VI data looks sane.
- **C. Interpreter semantics.** A branch/delay-slot/VI pipeline rule makes a
  finite loop infinite (e.g. VI written in the branch delay slot, or the
  integer-register pipeline latency around `IBNE`/`IBGTZ`). Signature: the
  data and flags look sane but the exit VI never reaches the exit value in
  the trace.

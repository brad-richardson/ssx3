# E61 — why are menus and loading slow? (Mac, muse, Part 1 evidence, 2 h)

## Goal
Every boot to the race walks title → menus → loading, and those phases run far below full speed even on the M5 Pro mini: title/startup **0.67×**, menus **0.54×**, loading/Rival card **0.17×** (E58, clean build, pre-sound fold; `local/research/E58/REPORT.md` Part 3). Menus are light scenes, so this looks like waste rather than real work. Faster menus shorten every test boot and Brad's own play. Part 1 finds where menu and loading time goes; the orchestrator picks any fix for Part 2.

## Hypotheses and the observable that separates them
| H | Mechanism | Observable |
| --- | --- | --- |
| H1 CPU work | a hot loop (VU1 on the 3D rider, GS CPU raster of full-screen layers, VIF/DMA) | GameThread ~100% busy; profile dominated by that stage |
| H2 waiting | the game thread blocks on host present/vsync, a sleep, a semaphore/RPC poll with a timed wait, or the audio clock | GameThread < ~90% busy in menus; profile shows wait/sleep/cond frames |
| H3 guest idle spin | guest polls (CD/IOP/SIF RPC, VSync wait loops) cost host time per iteration | profile dominated by syscall/RPC/scheduler helpers, guest code share high in loading |
| H4 loading I/O | CD read emulation paced or synchronous file reads | loading phase: time in CD/ISO read paths, low CPU |

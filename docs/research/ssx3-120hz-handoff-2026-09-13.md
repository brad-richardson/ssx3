# SSX3 / 120 Hz handoff

*RESEARCH SNAPSHOT  •  13 SEPTEMBER 2026  •  DOLPHIN / GAMECUBE + RECOMP*

> **Recommended first move:** trace scheduling and replay/render-state boundaries before changing physics or training a model. Existing SSX3 patches provide concrete timing leads; they do not establish that native 120 Hz already works.

**Goal:** smoother 120 Hz presentation on Android and iOS while preserving SSX3’s gameplay. Investigate true higher-rate updates, original-rate simulation with interpolated rendering, and learned frame interpolation as separate options.

## What the public projects actually contain

| Project | Observed state / practical value |
| --- | --- |
| ssxdecomp/ssx3_gc [1,2] | GameCube GXBE69. Head ec889b87b0, 1 July 2025. The inspected src tree contains two C files and one header. Useful setup, symbols and a few recovered routines—not a completed game engine. |
| ssxdecomp/ssx3 [3,4] | PS2 NTSC-U SLUS_207.72. Head 9cd4626054, 20 March 2026. Valuable named addresses and source layout; src/bx/appman.cpp is only a placeholder comment. |
| SSXModding/SSX-Patches [5] | Actual PS2 patches for performance frame-skipping and 60 fps two-player mode. Stronger starting points than an indiscriminate search for 1/60 constants. |
| GlitcherOG/SSX-Library [7] | C# asset tooling, being refactored for cross-platform use. Lists SSX3 GameCube model readers and PS2 level/trigger/visibility readers. Not a replacement runtime engine. |
| ssxdecomp/ssx; ssxdvd [6] | Sibling PS2 SSX and Tricky decomps. Useful family vocabulary and comparison material; neither proves SSX3’s timing behavior. |
| SSXModding/SSX-ElfLdr [8] | PS2 mod-loader infrastructure: an optional comparison lab, not the GameCube or mobile implementation path. |

## What changes the investigation

**Scheduling:** a published split-screen patch changes a location inside the address interval beginning at the named PS2 main loop. **State capture:** symbols include replay restoration, rider/AI replay readers, a render-state reader and a separate HUD render callback. These are promising boundaries to inspect—not proof that replay already interpolates. [4,5]

Do not choose an engine architecture from a guessed middleware label. The inspected material provides concrete BX, cSSXApp, cWorld, animation, UI, streaming and replay names to search instead. [2,4]

> **Evidence boundary:** public source and metadata inspection only. No user repository, game disassembly, build, patch or mobile benchmark was tested. The original simulation rate is unverified; “60 Hz simulation” is an example until measured. A matching decomp is not automatically a native port.

# 01 / Concrete entry points

*COMMUNITY LABELS AND PATCH LOCATIONS, NOT INDEPENDENTLY VALIDATED DISASSEMBLY*

## PS2: start with the known scheduling modifications

In **PS2/SSX 3/SLUS-20772_08FFF00D.pnach**, “Fix Metro Slowdown” (Meridian) writes zero at **0x00230704** and **0x00230710**, described as disabling performance frame-skip. “60 FPS 2 Players” (Gabominated) writes **0x26310002** at **0x00317184**. These are published patch claims, not results reproduced for this handoff. [5]

**Useful inference:** 0x00317184 is +0x284 from cAppMan_mainLoop and precedes the next named cAppMan_checkHalt at 0x00317328. Disassemble that interval to identify the loop counter, divisor or scheduling branch. Do not infer its semantics from the patch title alone. [4,5]

| PS2 label | Address | Question to answer |
| --- | --- | --- |
| cAppMan_mainLoop | 0x00316F00 | Where are update, render and wait separated? |
| cSSXApp_preUpdate<br>cSSXApp_timerCallback | 0x00227E98<br>0x00227F58 | Which clock and timestep reach the game? |
| cGameViewMan_updateAll | 0x0022E840 | Per-view work, camera work or simulation? |
| cReplay_restoreFrame | 0x0026DBF0 | What complete state can be recovered? |
| cRenderStateMan_<br>readFromReplayFrame | 0x002EF2D8 | Is there a reusable render snapshot? |
| cAI_readFromReplayFrame | 0x0012B948 | What rider state is serialized? |

| cGraphicsMan_AddBlendedMatrix | 0x003698E0 | Skinning/blending clue—not proof of temporal interpolation. |

All PS2 labels above come from config/symbol_addrs.txt at the pinned PS2 revision. [4] **None of these addresses or MIPS instructions transfers directly to GameCube PowerPC.** Match behavior, call structure and data references in the target binary.

| Source-comment label | GXBE69 address | Use |

# 02 / First working-session runbook

*INSTRUMENT FIRST; CHANGE ONE TIMING AXIS AT A TIME*

## A. Fingerprint and establish a repeatable baseline

Use a scratch save and reversible patches with original-byte checks. Record game region/revision, executable hash, emulator/recomp commit and patch set. The GC decomp config expects **orig/GXBE69/sys/main.dol**, SHA-1 **5aae61dc3bd5c7abb92d158c4477f1a9ca4de385**. A mismatch requires re-identifying addresses, not forcing the patch. [1]

Import the local symbol map into the debugger/disassembler. Start from application callbacks and trace callers of timing, input, update, draw and wait functions. Count **simulation steps, game renders, video-interface events and host presents separately**, per unit of guest time. Also inspect timestep values and unique scene changes; a 120 fps counter can describe repeated frames.

```text
rg -n 'AppMan|timerCallback|preUpdate|Replay|RenderState|Frame|VSync|VIWait' \
  config/GXBE69/symbols.txt
```

Capture the same initial state and time-stamped input sequence twice. Establish normal run-to-run variability before calling later drift a regression. Suggested trace fields:

```text
wall_ns, guest_time, sim_step_id, render_id, present_id, dt
input_sequence, rider_position, velocity, rider_state, trick_timer
camera_pose, animation_phase, RNG_state_or_call_counts
streaming_flags, camera_cut, GPU_timestamps
```

## B. Run the smallest discriminating experiment matrix

| Experiment | Simulation / timestep | What it establishes |
| --- | --- | --- |
| Baseline | Unmodified cadence and dt | Original behavior and actual update rate |
| Render decimation | Original simulation; render half as often | Whether reduced rendering changes gameplay |
| Deliberately wrong control | Half update cadence; unchanged dt | Failure signature of cadence-dependent advancement |
| Time-normalized 30 test* | Half update cadence; doubled dt | Which systems honor a common timestep |
| Time-normalized 120 test* | Double update cadence; halved dt | Candidate native-rate behavior and remaining outliers |
| Render-only 120 test* | Original simulation; two draws per step | First test repeatability, then interpolate render state |

*30/120 labels assume a measured 60 Hz baseline. Preserve the guest timebase while altering the selected scheduler path. **Emulator turbo, host refresh, CPU overclock and game timestep are different controls.** Faster whole-machine emulation is not a valid variable-timestep test; CPU overclock may only supply execution headroom.

## C. Compare gameplay, not just a stopwatch

Use stationary camera motion, a repeatable downhill section, a jump/trick, a rail, a crash/reset and a streaming boundary. Compare distance, speed, airtime, trick windows, animation phase, camera response, audio and event counts against elapsed game time. Keep input edges at the same game-time coordinates—not the same frame numbers. Replays themselves need timing validation.

> **First-session deliverables:** one timing/call graph; a CSV trace and baseline capture; a list of verified hook addresses with expected original bytes; and a recommendation for native updates, render-state interpolation or image interpolation. Do not globally replace every 1/60 constant.

# 03 / Prefer a render-state seam

*PRESERVE ORIGINAL GAMEPLAY UNTIL MEASUREMENTS JUSTIFY CHANGING IT*

## A targeted decomp can be enough—but find the right boundary

Prioritize scheduling, game update, camera/view state, rider pose, scene draw and HUD composition. Inspect the replay readers’ fields, object identities, animation and VFX coverage. Replay existence does not establish fractional-time playback; these labels identify where to investigate. [4]

Prototype a static-world camera sweep with rider/VFX held fixed. Then add rider-root interpolation, skeletal animation and effects. Model, camera-trigger and visibility readers can help construct controlled cases; check each reader’s platform support. [7]

## Proposed integration contract

```text
simulation: previous = current; run_original_update()
            current = capture_render_snapshot()
display:    render(interpolate(previous, current, alpha))
            compose_hud_for_the_same_display_time()
```

This is pseudocode, not an SSX3 API. Use immutable snapshots, stable object IDs and generation counters. Interpolate positions, rotations and local skeletal transforms; rebuild matrices. Do not blend arbitrary matrix elements or write poses back into live physics. Previous/current-state interpolation is a standard fixed-timestep rendering pattern. [11]

**Latency is not free:** previous/current interpolation normally displays a historical state. Its delay depends on scheduling, often on the order of a simulation step. It cannot use an unknown future state. Extrapolation can reduce that delay but becomes prediction and needs correction at impacts, turns and cuts.

## Audit these before calling the result correct

**Render side effects.** Draw twice without an update and compare scoped gameplay state, RNG calls, animation advancement, particles, trails, streaming requests and audio events. Render caches may legitimately change; gameplay must not advance twice.

**Visibility and discontinuities.** Handle camera cuts, respawns, object birth/death, LOD switches and streaming changes explicitly. Interpolate bone/board attachments together; preserve timed trail points and particle lifetimes. Recompute culling for the interpolated camera or prove existing visibility is conservative enough.

**Dolphin versus a native renderer.** Replaying captured graphics commands is not the same as re-rendering a world snapshot. Commands may already contain transformed vertices and a visibility-filtered draw list. Establish access to scene state or an adequate retained draw representation before assuming a second correct viewpoint is available.

## When timing really must change

Recover timestep consumers and event counters, not just constants. For smoothing x += a × (target − x), its constant-target response is preserved by **a_new = 1 − (1 − a_old)^(dt_new/dt_old)**, not simply halving a. Collision solvers, trick rules and discrete events still need behavioral tests.

> **Decision gate:** prefer original-rate simulation plus rasterized interpolation when the state seam is clean and two renders fit. Prefer native higher-rate updates only after gameplay regression tests pass. Revisit image interpolation when state extraction or rendering cost dominates.

# 04 / A game-specific model is the fallback experiment

*BASELINE FIRST; VALID TEMPORAL LABELS MATTER MORE THAN MODEL NOVELTY*

## What “like DLSS” means here

The analogy is **DLSS Frame Generation**, not Super Resolution. NVIDIA’s documented DLSS 3 design combines frames, optical flow and engine information in learned interpolation. Use it as an architectural reference, not a mobile dependency or a description of every later DLSS feature. [9]

First test pretrained RIFE on SSX3 captures. RIFE’s IFNet predicts intermediate flow and supports a temporal interpolation parameter; this is a much better baseline than immediately training an RGB generator from scratch. [10] A proposed SSX-specific student could predict midpoint-to-endpoint sampling flows, visibility/blending weights and a small residual:

```text
I_mid = m * warp(I0, F_mid_to_0)
      + (1 - m) * warp(I1, F_mid_to_1) + residual
```

Predict sampling directions explicitly; half an endpoint flow is not automatically the correct backward sampling field. Supply depth and renderer motion only after their coordinate conventions and validity are verified. A narrow game domain may help, but does not guarantee a tiny model or recover surfaces hidden in both inputs.

## Build the dataset without fooling yourself

| Capture | Valid learning claim |
| --- | --- |
| Unmodified 60 fps: (F0, F2) → F1 | A supervised 30→60 task: endpoints are about 33.3 ms apart. Useful baseline, but not matched 60→120 ground truth. |
| Coherent game-time samples at 0 / 8.3 / 16.7 ms | Potential 60→120 supervision. Requires validated substep rendering/timing, or a clearly defined render-state interpolation target. |
| Turbo, duplicated frames, or slowed playback | No new intermediate states. A “broken 120” build is useful only where its local motion and labels have been independently validated. |

Split validation by complete runs/locations/camera sequences, not adjacent frames. Include fast trees and rails, rider tricks, snow spray, shadows, cuts and streaming transitions. Judge temporal flicker and motion boundaries in video, alongside reconstruction metrics. Keep HUD and split-screen boundaries out of interpolation once a reliable composition boundary is available.

## Mobile acceptance gate

Keep one model/algorithm contract behind native graphics adapters. **MNN** is a candidate runtime: its project documents Android/iOS and Metal/OpenCL/Vulkan inference. Operator coverage, warp/grid-sampling behavior, texture interop and CPU fallbacks must be profiled on the chosen devices. Platform support is not a guarantee that this model runs within budget. [12]

Measure warmed-device GPU time, transfers, synchronization, inference, warp, UI and present intervals. A 60→120 pipeline has 16.67 ms per two-frame cycle on average, but must also meet individual 8.33 ms presentation deadlines. Compare against native 60 and the raster-interpolation prototype; report latency and sustained thermal behavior, not only average fps.

MetalFX is an optional Apple comparison backend; its documented inputs include frames, depth and motion, with separate UI handling. [13] Bidirectional ML also waits for the second frame: budget lookahead latency. On cuts, missing history or missed deadlines, fall back to native-rate presentation.
